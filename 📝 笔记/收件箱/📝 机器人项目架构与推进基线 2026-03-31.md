## 二、真实系统架构

### 1. 主机侧

- 当前对话所在系统是笔记本 Ubuntu 22。
- 主机侧承担机器人描述、SLAM/EKF、多传感器融合、RTAB-Map 定位/建图、Nav2 单路点导航等上层能力。
- 主机侧真实运行工作区为 `~/ros2_ws`。

### 2. 香橙派侧

- 香橙派 5 Plus 也是 Ubuntu 22。
- 香橙派侧承担真实硬件接入与底层数据骨干：底盘串口桥、IMU、雷达、相机。
- 主控入口在 `orangepi_src/my_robot_launch/launch/robot_launch.py`。

## 三、主控侧代码要点

### 1. 启动分组

`my_robot_launch/launch/robot_launch.py` 将系统分为两组：

- `move`：底盘串口桥 + IMU
- `see`：激光雷达 + Astra 相机 + 图像压缩

### 2. 底盘驱动

`chassis_driver/chassis_driver/serial_bridge.py` 的关键信息：

- 订阅 `cmd_vel`
- 发布 `wheel/odom`
- 通过串口与 STM32 通信
- 做三轮全向底盘的正运动学解算
- 当前底盘不是差速，而是三全向 / 全向底盘模型

### 3. IMU

`imu_odometry/imu_odometry/imu_node.py` 的关键信息：

- 发布 `/imu/odom`
- 已针对 EKF 融合做过协方差配置
- 当前策略更偏向让 IMU 锁定航向与角速度

## 四、主机侧代码要点

### 1. 机器人描述

`my_robot_description` 提供 URDF 与 TF 基础：

- `rsp_launch.py` 负责 `robot_state_publisher` 和静态 TF
- `omni_car.urdf` 已定义雷达、相机、IMU 的安装位姿
- 该 URDF 对后续跟随坐标系、盲区、传感器相对位姿判断很关键

### 2. 状态估计与 SLAM

`my_robot_slam` 当前具备：

- RTAB-Map 建图 / 定位
- 视觉里程计 `rgbd_odometry`
- 激光里程计 `icp_odometry`
- EKF 融合

`efk.yaml` 当前融合思路：

- `wheel/odom` 主要提供 `vx / vy`
- `/imu/odom` 主要提供 `yaw / vyaw`
- `/vision/odom` 和 `/lidar/odom` 作为补充与修正来源

### 3. 导航

`my_robot_navi` 当前已具备：

- RTAB-Map 只读定位接 Nav2
- Nav2 单路点导航
- 代价地图与局部规划参数已存在

## 五、当前项目阶段判断

当前系统已经具备以下能力：

- 硬件接入通了
- `/cmd_vel -> 底盘 -> /wheel/odom` 闭环通了
- IMU / 视觉 / 激光的状态估计链路通了
- Nav2 单路点导航已经可用

当前缺失的是“上层行为控制”部分：

- 没有独立的雷达跟随节点
- 没有导航模式 / 跟随模式 / 遥控模式的仲裁层
- 没有顶层状态机去实现任务切换
- 没有真正贴合当前三全向底盘的小车雷达跟随控制逻辑

## 七、后续推进原则

### 1. 明确实施边界

后续正式改代码时，只在 `~/ros2_ws` 中推进，不在 `codex_ws` 的资料库里直接开发功能。

### 2. 先做什么

最合理的下一步不是继续堆 SLAM 或 Nav2，而是新增一个“雷达跟随控制层”。

建议顺序：

1. 在 `~/ros2_ws/src` 新建一个独立的跟随控制包
2. 第一阶段只做纯雷达跟随最小闭环：`/scan -> 目标提取 -> /cmd_vel`
3. 先不接视觉融合，也不先写状态机
4. 跟随后再做导航 / 跟随模式切换
5. 最后再接顶层任务调度

### 3. 控制设计原则

- 因为当前底盘是三全向，第一版跟随逻辑应保留 `vy` 横移能力，不要按差速车去设计
- 跟随节点应与 Nav2 解耦，避免把行为控制硬塞进现有导航包
